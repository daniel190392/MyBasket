# Architecture: design system library modules

Applies to every module under `modules/` named `ui-*` (e.g. `ui-components`, `ui-animation`). Modules of this type are **design system libraries**, not applications. Do not apply app patterns (MVVM, Clean Architecture, global state) here.

## Naming convention

- Design system library modules are named `ui-<topic>` (kebab-case). The `ui-` prefix is what scopes this rule to them, so new modules are covered automatically.
- Each module has its own short component prefix (e.g. `P`), unique across modules to avoid name collisions for consumers.
- Modules that are not design system libraries (feature modules, native hosts) must **not** use the `ui-` prefix.

## Layers

Dependencies flow in one direction only:

```
theme (tokens)  →  components
```

- `theme/`: design tokens (colors, spacing, typography, borders, shadows, motion). Depends on nothing.
- `components/`: reusable UI building blocks. They consume tokens and never the other way around.
- Composite components (built from other components) may depend on basic components, never the reverse.
- Between modules: a `ui-*` module may depend on another `ui-*` module only if the dependency is declared in its `package.json` and there is no cycle. Prefer sharing tokens through one module rather than duplicating them.

## Rules

1. **Presentational and domain-free.** Components receive data and callbacks through props. They must not know about the app domain (products, expiration dates, inventory), navigate, call APIs, or read app state. Domain logic belongs to the app or feature modules.
2. **Internal state is UI-only** (focus, pressed, open/closed, animation progress). Application state is owned by the consumer.
3. **Minimal, stable public API.** Everything public is exported from `src/index.ts`. Consumers must not deep-import internal files. Treat changes to exports and props as API changes (they can break consumers).
4. **Prefer composition over configuration.** Use slots (`leftIcon`, `children`) instead of piling up boolean props.
5. **Extend native props.** Props types extend the underlying React Native props and forward the rest, so consumers keep full control.
6. **Tokens only.** No hardcoded colors, spacing, font sizes, radii or durations/easings in components; use `theme`.
7. **No heavy dependencies.** `react` and `react-native` are `peerDependencies`. Adding any other runtime dependency needs explicit approval.
8. **Typed events and props.** No `any` in public props or event handlers; use React Native event types (e.g. `FocusEvent` and `BlurEvent`, which replace the deprecated `NativeSyntheticEvent<TextInputFocusEventData>`).
9. **Every component has a showcase screen** in the module's `example/` documenting its variants and states.

## Structure

- Start flat: `src/components/<Component>.tsx`, `src/theme/*.ts`, `src/index.ts`.
- Move to one folder per component (`<Component>/<Component>.tsx`, styles, tests, `index.ts`) only when a component grows large or gets its own tests.
- Do not introduce a `ThemeProvider`/context until multiple themes or dark mode are required.
- Do not adopt Atomic Design folder layers (atoms/molecules/organisms) at this size.

## Build output

- `lib/` is generated by `npm run build` (`tsc` + `react-native-builder-bob`). Never edit it by hand. After changing `src/`, rebuild so `lib/` does not go stale while it is still versioned.
